# iPhone 滑动清理与双向同步设计

日期：2026-11-09
状态：设计已在对话中确认，待审阅本文
范围：第一版 iPhone App + 局域网电脑桌面程序

## 1. 目标

做一个 iPhone App 和一台局域网电脑上的桌面程序。手机全屏上下滑动整理相册，确认删除的是两端都不要的照片。电脑上用户选定的一个文件夹是另一端的同一套照片和视频。

已确认的产品规则：

- 第一版平台是 iPhone。Mac 只负责编译、签名和安装验证。
- 备份位置是局域网电脑文件夹，Mac 或 Windows 都可以。
- 同步是双向的：新增、修改、删除两边互相同步。
- 在 App 里确认删除后，电脑文件夹中的对应文件一并删除。

一次成功的同步会话结束后，iPhone 相册里参与同步的资产，和电脑文件夹里参与同步的文件，指向同一批内容。

## 2. 不做什么

- 不修改现有 Android 应用、Go ZIP 服务和浏览器下载页。它们继续做一次性迁移。
- 不把 ZIP 流式下载扩展成同步协议。
- 不做 HEIC 转 JPG，也不做转码。同步的是选定资源的原始字节。
- 不做「只删手机、电脑留档」。
- 不做云账号、NAS 专用协议、付费墙、Android 滑动客户端、iPad 专用界面。
- 不在本规格里改许可证，也不提交 App Store。仓库仍是 GPL-3.0。上架前的许可决定单独处理。
- 不把连拍合并成一条。每个 `PHAsset` 独立同步。
- 不做跨机器文件夹锁。一个文件夹只运行一个桌面程序。

## 3. 运行条件

同步只在下面两件事同时成立时进行：

- iPhone App 在前台。
- 电脑上的桌面程序正在运行，并且正在监听。

锁屏、切到别的 App、或桌面程序没开，传输暂停。下次两边都就绪时，从已校验通过的块继续。未通过整文件 SHA-256 的数据不算同步完成。

听端口的是桌面程序。手机是客户端。iOS 不承担长期后台传文件。

桌面程序用 Bonjour 服务类型 `_photosmove-sync._tcp` 广播，默认 TCP 端口 `53621`。手机也可以手输电脑 IP。这个服务类型和端口与现有 Android 迁移服务分开。

传输走局域网 HTTP，不使用云。配对成功前使用 4 位 PIN。配对成功后使用长期设备令牌。令牌放在 `Authorization: Bearer` 头里。PIN 显示在桌面程序上，由手机输入。

第一版要求 iOS「所有照片」权限。用户拒绝或只授权部分照片时，App 停在权限说明页，不建立同步会话。有限授权看不见的资产无法删除，镜像会是假的。

部署目标：iOS 16.0。增量变更使用 `PHPersistentChangeToken`。

界面语言跟随系统，提供 `zh-CN` 和 `en`。

## 4. 组件

### 4.1 iPhone App

路径：`photosmove/ios/`

职责：

- 用 PhotoKit 枚举相册资产，读取和写入照片。
- 全屏滑动整理，把保留和待删标记存在本机。
- 作为同步客户端，上传、下载、确认删除。
- 把设备令牌放在 Keychain。整理进度只存在本机，不同步。

它不监听局域网端口，不选择电脑文件夹。

### 4.2 桌面程序

路径：`photosmove/desktop/`

职责：

- 让用户选定一个文件夹，并只在该文件夹内读写。
- 保存同步索引，监视文件夹变化。
- 作为局域网服务端，完成配对、索引交换和分块传文件。
- 对手机确认过的删除，删除对应文件。
- 把文件夹里的新增和修改提供给手机导入。

技术：Go，索引使用 SQLite。Mac 和 Windows 各构建一个可执行文件，协议相同。

### 4.3 现有迁移工具

`photosmove/android`、`photosmove/server`、`photosmove/web` 不进入本功能。可沿用的只有既有概念：一次性 PIN、之后的令牌，以及用 SHA-256 作为文件完整性单位。

## 5. 身份与文件布局

### 5.1 三层身份

| 名字 | 含义 |
|---|---|
| `pairId` | 小写 UUID v4。第一次把两端连起来时生成，两边都保存 |
| 手机键 | `PHAsset.localIdentifier` |
| 电脑键 | 同步文件夹内的相对路径，使用 `/` 分隔 |
| 内容 | 每个资源的 SHA-256，64 位小写十六进制 |

一个 `pairId` 在手机上对应零个或一个资产，在电脑上对应这个资产的全部资源文件。Live Photo 是一个 `pairId` 下的两个文件。

### 5.2 资源选择

非 Live Photo 的照片或视频，只同步一个当前完整资源：

- 没有编辑：同步原始资源的字节。原始资源是 RAW、DNG、HEIC 或 JPEG 时，同步的就是该原始资源。同一资产上的备用 JPEG 或备用 RAW 不另存为第二个文件。
- 有编辑：同步用户当前看到的完整尺寸渲染结果，替换电脑上的文件。不同步编辑栈，电脑上不能继续用「还原原图」回到 Photos 的调整记录。
- 视频：同步当前完整尺寸视频资源。

Live Photo 同步两个资源，角色固定为 `image` 和 `pairedVideo`。两个资源都读到字节并完成哈希后，这个资产才算可同步。缺了配对视频时，该资产保持未同步，界面标出失败，不同步单独的静图。

资源尚未在本机时，App 在前台向照片图库请求数据。系统因此可能从 iCloud 下载。下载失败时，该资产保持未同步并出现在失败列表里，不假装已经备份。

### 5.3 电脑目录

磁盘路径是存放位置。相册成员关系另存在索引里。

用户相册指 `PHAssetCollectionTypeAlbum` 且 `PHAssetCollectionSubtypeAlbumRegular` 的相册。最近项目、收藏、视频、自拍、截图等智能相册不作为文件夹名。

主文件夹：

- 资产属于至少一个用户相册：取这些相册标题里字典序最小的一个。
- 不属于任何用户相册：`Recents/`。

索引保存该资产的全部用户相册标题、是否收藏、拍摄时间。电脑侧替换导致手机重新导入时，按这份列表把资产加回同名用户相册，并写回收藏和拍摄时间。同名用户相册不存在时，手机创建同名普通用户相册再加入。

相册标题和文件名写入路径前做规范化：去掉首尾空白；`/`、`\`、`:` 和控制字符换成 `_`；空标题写成 `Album`；以 `.` 开头的标题去掉开头的点后再应用空标题规则。文件名只用资源原始文件名的最后一段。手机不得提交绝对路径或 `..`。

重名：同一文件夹里，文件名已被另一个 `pairId` 使用时，在扩展名前加上 `-` 和 `pairId` 的前 8 位。原始文件名为空时，使用 `{pairId}` 加从资源类型得到的扩展名。

Live Photo 两个文件使用同一个主文件名，扩展名保持各自资源的扩展名。

### 5.4 桌面程序自己的文件

这些路径在同步文件夹内，监视器忽略它们，手机也不导入：

- `.photosmove/device.json`：文件夹 UUID、协议版本
- `.photosmove/index.sqlite`：索引
- `.photosmove/partials/`：未完成的块
- 任何以 `.partial` 结尾的文件

`device.json` 在用户第一次选定文件夹时创建。拷贝整个文件夹会拷贝这份身份。第一版不检测另一台电脑是否也打开了同一文件夹。

## 6. 配对与会话

1. 桌面程序生成 4 位 PIN，并在界面上显示。
2. 手机提交 PIN。成功后两边保存新令牌，旧令牌立即失效。令牌是 32 字节随机数的 64 位小写十六进制。同一 IP 连续 5 次 PIN 错误后，10 分钟内拒绝配对。
3. 一个文件夹同时只绑定一部手机。新手机配对会替换绑定。新手机的本机索引从空开始，电脑索引保留。
4. 换机后的第一次会话按 SHA-256 重新绑定。哈希对上的电脑文件沿用原 `pairId`，并记下这部手机的新 `localIdentifier`。哈希对不上的电脑文件也沿用它已有的 `pairId`，作为电脑新增导入这部手机。没有 `pairId` 的新文件才创建 `pairId`。已经不在这部手机上的旧资产，不因此删除电脑文件。

握手要求协议版本等于 `1`。版本不同则拒绝会话，两边界面显示版本不一致。没有第二套协议。

路径穿越、文件夹外写入、令牌错误，桌面程序拒绝该请求并且不改索引。

## 7. 同步规则

### 7.1 变更记录

每一侧为每个 `pairId` 保存：

- `localGeneration`：本侧代数，单调递增的 `int64`
- `remoteAckedLocalGeneration`：对端已经落盘应用的本侧代数
- `appliedRemoteGeneration`：本侧已经落盘应用的对端代数
- 当前每个资源的 SHA-256、大小、相对路径或 `localIdentifier`
- 用户相册标题列表、收藏、拍摄时间

操作日志条目包含：`opId`、来源（phone 或 desktop）、种类（add、replace、delete）、`pairId`、该侧新代数、内容哈希、创建时间。

接收方只有在本机状态已经落盘后才发送确认：电脑是文件 `fsync` 且索引已写入；手机是 PhotoKit 变更已提交且索引已写入。确认前中断，下次会话重做这一条，不产生第二份已确认内容。

### 7.2 首次对齐

两边都做全量枚举。

- 哈希完全相同的手机资产和电脑文件连成同一个 `pairId`。两侧 `localGeneration`、`remoteAckedLocalGeneration`、`appliedRemoteGeneration` 都设为 1，不传字节。
- Live Photo 必须 image 和 pairedVideo 两个哈希都相同才算同一个 `pairId`。
- 哈希不同的项按新增处理，向另一端传输。
- 旧迁移工具如果把 HEIC 转成了 JPG，哈希不同，按两份内容处理，不做模糊匹配。

电脑侧用大小和修改时间决定是否重算哈希。大小和修改时间都没变时沿用已存哈希。只有修改时间变了、哈希没变，不算修改，不传播。

手机侧在令牌有效时使用 `PHPersistentChangeToken` 取增量。令牌失效时全量重扫，再用 `localIdentifier` 和哈希重新连接。

### 7.3 普通操作

| 情况 | 动作 |
|---|---|
| 只有手机新增 | 上传选定资源的字节，电脑按第 5.3 节写入 |
| 只有电脑新增 | 手机导入相册并记下新的 `localIdentifier`。文件已有 `pairId` 则沿用，否则创建 |
| 只有一端删除，另一端没有未确认修改 | 另一端删除 |
| 两端都删除 | 两边删除完成并确认 |
| 两端都改了，哈希不同 | 两份都保留 |
| 一端删除，另一端有未确认修改 | 保留修改过的那份，删除不执行 |

电脑新增的文件必须属于第 9 节的扩展名。其他文件、`.AAE`、`.xmp` 忽略。

修改指同一个 `pairId` 的选定资源 SHA-256 变了。相册标题、收藏或拍摄时间变化也写入对端，不更换文件字节。只有元数据不同时，采用手机侧的相册列表、收藏和拍摄时间，并写回电脑索引。元数据规则不合并内容字节。电脑新文件没有拍摄时间记录时，使用文件创建时间；没有创建时间则使用修改时间。

电脑文件被替换时，手机删除旧资产并导入新字节，保持同一个 `pairId`，再按索引恢复用户相册、收藏和拍摄时间。

### 7.4 冲突

同一 `pairId` 在会话开始时，两侧都有对端尚未确认的内容变更，并且两侧内容哈希不同：

- 原 `pairId` 改绑到手机版本。手机资产不变。电脑把手机字节另存为新文件，扩展名前加 `.phone-` 和哈希前 8 位。原电脑文件不再属于这个 `pairId`。
- 原电脑文件获得新的 `pairId`，并导入手机成为一条新资产。
- 两个 `pairId` 的两侧代数都设为已对齐。
- 界面列出这一对冲突。用户删掉不要的那一份时，按普通删除同步。

一端是未确认删除，另一端是未确认修改时：

- 不执行删除。
- 修改过的版本保留在原 `pairId`。
- 已经在手机上删掉的资产，用电脑版本重新导入到原 `pairId`。
- 已经在电脑上删掉的文件，用手机版本重新上传到原 `pairId`。
- 界面记录「另一端有新修改，已保留修改版本」。

### 7.5 删除时序

已连接时，用户在待删托盘确认删除：

1. 先在电脑删除该 `pairId` 的全部资源文件，并删除因此变空、且由桌面程序创建的目录。
2. 电脑确认删除已落盘后，手机再删除 `PHAsset`。
3. 两边确认该删除操作。
4. 电脑删除失败时，手机不删除，待删标记保留，界面显示失败。

未连接时，用户仍可以确认：

- 手机立即删除，并记下删除操作和删除当时的内容哈希。
- 下次连接时，电脑文件仍是该哈希，则删除电脑文件。
- 电脑文件哈希已经不同，则按第 7.4 节「删除对修改」处理，把电脑版本导回手机。

在照片 App 里删除，或在访达/资源管理器里删除文件，都在下一次成功会话里按同样的删除规则传播。App 不在前台时不传播。

确认删除的说明文字固定包含三句：

- 将从 iPhone 相册删除。
- 将从电脑同步文件夹删除对应文件。
- 若打开了 iCloud 照片，系统还会从 iCloud 和其他已登录设备删除。

不探测 iCloud 照片是否打开。第三句始终显示。

### 7.6 传文件

块大小 4 MiB。块写入 `.photosmove/partials/`。整文件 SHA-256 与索引一致后，才移动到第 5.3 节的最终路径并确认。

续传条件：已有 partial 的长度是已确认块的整数倍，且已确认前缀的哈希与发送方一致。否则删除 partial，从这个文件的第 0 块重传。

重复执行同一次已确认操作不产生第二份文件或第二份资产。

## 8. 滑动整理

默认流包含全部未隐藏的照片和视频，按拍摄时间从新到旧。拍摄时间相同则按 `localIdentifier` 升序。隐藏资产参加同步，不进入整理流。

视频进入画面后自动播放。声音跟随硬件静音开关。点按暂停或继续。

手势：

- 上滑：下一张。
- 下滑：上一张。
- 从画面内部开始的左滑：标为待删并前进。从屏幕左边缘开始的系统返回手势不标待删。
- 右滑：标为保留并前进。若该张此前待删，右滑清除待删标记。

标记只存在手机本机：

- `unseen`：还没处理。
- `keep`：保留。
- `pendingDelete`：待删。

退出后再打开，停在上次查看的资产。新照片按排序出现在流里，状态为 `unseen`。

待删托盘列出全部 `pendingDelete`。撤销弹出最后一条待删标记，将该资产设回 `unseen`，并把画面移到这张。确认作用于当前全部待删项，按第 7.5 节删除。只标记、不确认，不删除任何一端。

删除成功后，移除该资产的整理记录。

同步状态在画面上可见：未配对、传输中、已对齐、失败数、冲突数。失败和冲突可打开列表。

## 9. 电脑导入的扩展名

与现有扫描器的媒体扩展名一致，比较时忽略大小写：

- 图片：`.jpg` `.jpeg` `.png` `.heic` `.heif` `.gif` `.bmp` `.webp` `.tiff` `.tif` `.raw` `.dng`
- 视频：`.mp4` `.mov` `.avi` `.mkv` `.3gp` `.wmv` `.flv` `.m4v` `.mpeg` `.mpg`

Windows 可能无法预览 HEIC。第一版仍保存 HEIC 字节，不为此转码。

## 10. 构建与验证

iPhone 安装包只在 Mac 上用 Xcode 产出。Windows 工作区可以改代码，不能生成可安装包。实现阶段在已连接的 Mac 上执行 iOS 归档，并安装到真机。桌面程序的 macOS 版本也在该 Mac 上构建。Windows 版本在 Windows 上构建，或由 Mac 交叉编译；两种方式的协议和索引格式相同。

签名团队使用该 Mac 上已有的开发团队。规格不写入具体 Team ID。

桌面同步决策做成纯函数，用表驱动测试覆盖第 7.3 和 7.4 节的每一行，包括首次哈希合并、partial 续传条件、连接中删除失败时手机不删。

真机检查：

- 配对成功和错误 PIN 被拒绝。
- 一张未编辑照片、一张 Live Photo、一段视频完成对齐，字节哈希与手机资源一致。
- 已有相同哈希的电脑文件不再上传第二份。
- 确认删除后，手机资产和电脑文件都没有了；电脑删除失败时手机资产还在。
- 电脑放入一张新的受支持图片后，手机相册出现该图片。
- 传一半中断，再次打开后从已确认块继续，最终哈希一致。
- 两端都改同一 `pairId` 后，两边各能看到两份内容。
- 一端删除、另一端已改内容时，修改版本还在，并回到被删除的那一端。

## 11. 实现顺序

顺序是依赖关系，不是可选范围。前面的步骤没有达到自己的验收，后面的步骤不能声称完成。

1. 桌面程序：选文件夹、PIN、索引、Bonjour、分块收发、哈希确认。
2. iPhone：读取相册、配对、上传第 5.2 节的资源，Live Photo 作为一个单位。
3. 首次按哈希合并。
4. 滑动整理和待删托盘。确认后按第 7.5 节删除两端。
5. 电脑文件夹的新增和删除回写到 iPhone。
6. 修改替换和冲突保留。
7. Mac 上的 `xcodebuild` 归档和真机检查。

## 12. 验收

全部为真时，这版设计才算实现完成：

- 前台 App 和正在运行的桌面程序之间，新增、修改、删除会在下一次成功会话后到达另一端。
- 确认删除会删除 iPhone 资产和电脑对应文件。连接中电脑删除失败时，iPhone 资产保留。
- 同一内容不会因为重复同步而变成两份。
- 哈希未通过的文件不会显示为已同步。
- 冲突时两份内容都还在，直到用户删除其中一份。
- 现有 Android ZIP 迁移的代码路径没有被改成同步协议。
